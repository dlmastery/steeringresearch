## 2. Findings
### A. Dataset quality (PRIMARY)

**A1. The construction is exactly as described — I verified it in code, not from the docstring.**
`data.py:71-76` positives = each Attack_600 row's **last K sub-queries** of `multi_turn_queries`
(payload lands last, so it is included), `group = query_id`. Negatives switch on `condition`:
- `easy` (`data.py:87-105`): K user turns from ONE `HuggingFaceH4/ultrachat_200k` conversation
  (streaming, `train_sft`), `group = 10_000_000 + i`, `source='ultrachat'`.
- `hard` (`data.py:109-147`): `usable` (rows with >= K sub-queries) is shuffled and cut in half;
  positives from the first half, negatives from the second = that attack's **first (K-1)**
  sub-queries + **1 filler** (another negative-side attack's first sub-query). Halves are
  disjoint by `query_id`. Exactly-K enforced at `data.py:140`.

**The half-split IS the 298 ceiling.** 600 rows → ~596 with >=5 sub-queries → 298 per side.
That is arithmetic, not a data limitation.

**A2. The pool cap is stated honestly but was NOT maximised — this is the central finding.**
The lesson treats "Attack_600 has 600 rows" as the ceiling. It is not. Verified today:

### B. Correctness / completeness

**B1. `results_gemma_ablation.json` IS NOT PRODUCED BY ANY CODE IN THE REPO.** I grepped the
whole `steering_tutorials/` tree for `gemma_ablation`, `margin_over_bar`, `replication_verdict`
— the only hits are the README and the artifact itself. The runner writes **only**
`C.RESULTS_PATH` (`artifacts/results.json`, `run_cross_trajectory.py:534`) and its schema has
none of the keys `hidden`, `n_per_class`, `note`, `margin_over_bar`, `replication_verdict`.
The ablation artifact was **hand-authored**. Under CLAUDE.md §18.8 ("an artifact that cannot
be regenerated from the code beside it is not evidence") the entire §9.3 table and the
`HOLDS` verdict are **inadmissible as stated** — not necessarily wrong, but unverifiable.

**B2. The two artifacts are mutually destructive.** `RESULTS_PATH` is a constant. Running
`CT_EMBED=gemma python -m ...run_cross_trajectory` **overwrites `results.json`**, destroying
the MiniLM headline. There is no `--out` and no embedder in the filename. So the side-by-side
§9.3 comparison **can never be produced by the code as written**, in one run or two.

**B3. No pool/config fingerprint guard** (the fix `meerkat` received). `results.json` records
`embedder, gemma_layer, k, n_folds, seed` and per-condition actual `n_pos/n_neg` (good), but
no dataset revision, no pool hash, no `CT_N_POS`/`CT_N_NEG` request-vs-realised record.

**B4. THE EMBEDDING CACHE CAN SILENTLY RETURN STALE VECTORS — same defect class as §18.8.**
`_embed_samples` (`run_cross_trajectory.py:271-278`) keys the cache on **`(condition, embedder)`
only** — not seed, not K, not n. And `multiturn_jailbreak/embed.py:114-119`:
```python
def load_or_build(conversations, method, cache_path):
    cached = _try_load_pack(cache_path)
    if cached is not None and len(cached) == len(conversations):
        return cached
```
The **only** validation is the COUNT. Change `CT_SEED` and the hard half-split reshuffles
which attacks are positives — same 596 samples, same 2,980 rows — and the cached vectors are
**silently reused against the new labels**. `dim` is written into the npz and never checked on
load either. This is verbatim the documented failure "the embedding cache returned **stale
labels** under a key that ignored them." It has not necessarily fired here; it is unguarded.

**B5. The OOD arm throws away ~80% of every CSTM-Bench scenario, and README does not say so.**
`load_ood_cstm` (`data.py:257`): `texts = sorted(texts, key=len, reverse=True)[:k]` — it keeps
the **5 longest** sessions of a scenario that `config.py:31` itself describes as "**a set of
~26 sessions**". Verified: `traj_ood_minilm.npz` has 540 rows = 108x5. For the **`dilution`**
split — whose entire premise is that the signal is *diluted across many sessions* — selecting
the 5 most verbose sessions is close to the worst available selection rule. The near-chance
OOD result (0.48-0.57) is therefore **confounded with the truncation**. README §9.2 states the
negative flatly ("the constructed decompositions do not teach a detector that generalizes")
without this caveat. That conclusion is not supported by the measurement as run.

**B6. The OOD numbers are degenerate, not merely "near chance".** All four methods report the
**identical** `f1 = 0.65` and `acc = 0.4815` — that is exactly the all-positive predictor
(precision 52/108 = 0.481, recall 1.0 → F1 0.65). And `mean_agg` has `auc = 0.5` with
`auc_ci = [0.5, 0.5]` — a **constant output** across all 108 scenarios, not a random one.
Mechanism (verified in `models.py:212-214, 242`): `MeanAgg` standardizes `[mean, max, std]`
features by the **train** `mu`/`sd` with no clipping; CSTM-Bench session texts are far longer
than 5 ActorAttack sub-queries, so the standardized features land far outside the fitted
range and the MLP logit saturates. "Near chance" and "saturated to a constant" are different
failures and the README reports only the first.

**B7. Minor doc-vs-code drift.** README §2 and §5 describe `mean_agg` as "mean-pool the K
embeddings -> standardize -> MLP". `models.py:198-204` actually pools **`[mean, max, std]`**
(3 x dim). Since `mean_agg` is the *top* method under both embedders, the description of the
winner is inaccurate — and its per-dimension `max` component is worth naming, because a `max`
term is exactly what the lesson's narrative says an aggregator does *not* need.

**B8. Things that are genuinely right, and should be said.** Group-aware `GroupKFold` by
`query_id` with seeded group remapping (`run_cross_trajectory.py:41-70`) — correct, and the
`k = min(n_folds, n_groups)` guard is sound. Bootstrap CIs skip degenerate single-class
resamples. `results.json` is written **before** the summary print (§17 playbook rule 3).
Stdout is ASCII-only. Every stage is exception-wrapped so a partial run still produces an
artifact. The falsifier is printed by the runner itself, so it cannot be quietly dropped from
the README. `per_traj_max` is a genuinely strong baseline (lesson-1's probe), not a straw man,
and §10 says so.
