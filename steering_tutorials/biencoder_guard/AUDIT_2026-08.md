## 2. Findings

### A. Dataset quality — the primary focus

#### A1. The "three pooled datasets" is really one dataset. MEASURED.

`data.py` docstring, `config.py` docstring, README §4 and README §6 all describe a
three-way pool. What actually lands in the corpus, from the live loader:

```
source dist: beavertails=4852, beavertails_benign=500, toxicchat=374
[data] wildguardmix SKIPPED (gated/unavailable: ... error 403)
corpus N=5726  policies=16  benign=500  mean_chars=435.4
```

- **BeaverTails: 5,352 / 5,726 rows = 93.5 %.**
- **toxic-chat: 374 rows = 6.5 %**, and it contributed **zero** benign rows.
- **wildguardmix: 0 rows.** HTTP **403** — gated, and this host has no HF token. It has
  never loaded; `datasets--allenai--wildguardmix` is absent from the hub cache while every
  other dataset the course uses is present.

The wildguardmix skip is *disclosed* in the code comment and in the README §6 table cell
("skipped gracefully if gated"), so this is not a hidden failure. But the README's
**prose** three sentences later is written in the indicative as if it happened:

> "wildguardmix supplies adversarial-but-benign prompts, the leakage-free style of hard
> negative" … "toxic-chat supplies genuine messy user prompts **and the benign
> hard-negatives that look adversarial but are safe**"

**Both clauses are false in the run that produced `results.json`.** toxic-chat's benign
backfill is gated behind `deficit = max(0, n_benign - bt_benign)`, and BeaverTails fills
the entire 500 quota first, so `tc_benign` is **0** by construction whenever
`N_BENIGN <= 500`. **Every benign row in this corpus is a BeaverTails safe row.** The one
design property the lesson advertises for its negatives — in-the-wild adversarial-looking
benign text — is not in the data.

`results.json` records **no source distribution and no per-column counts**, so a reader
cannot detect any of this from the artifact. That is the §18.8 pattern: the failure is
silent at the artifact layer even though it is loud on stderr.

Two structural consequences, neither discussed anywhere in the lesson:

1. **The harmful side is uncapped, the benign side is capped.** `_load_beavertails` keeps a
   multi-label row if *any* of its columns is still under quota, so common columns overshoot
   to 1,870 while `n_benign` stops dead at 500. Result: **5,226 vs 500**. `binary_harm_auc`
   (0.589 / 0.603 / 0.490 / 0.588) and `length_auc` (0.5264) are both computed on an 11:1
   set, and no prevalence-aware framing is offered for either.
2. **`jailbreak` at 109 positives is the lesson's own thesis column.** The whole framing is
   "adversarial prompts that try to bypass safety rules". It is the single most starved
   column in the taxonomy, and it is the only column for which the *adversarial* dataset
   was supposed to help.

#### A3. Hard-negative mining is mining ~69 % of the entire benign pool.

`results.json` `hardneg.n_mined = 240` = 12 seen policies x `HARDNEG_PER_POLICY=20`. The
train split holds roughly **350** benign rows (500 x 70 %). So "the 20 benign texts closest
to each policy" is drawing **~240 of ~350 available benigns** — the mining is nearly a
no-op, because there is almost nothing to *not* select. ANCE-style dense mining is only
meaningful when the negative pool is orders of magnitude larger than the selection.

This also explains the degenerate EXP-F baseline: `fpr_at_recall90` for the frozen
bi-encoder is **1.000** — at the threshold needed for 90 % recall it flags *every single*
hard negative. Falsifier (iii) "SURVIVES" against a baseline pinned at the literal
worst possible value. That is a true statement about a very low bar, and the README does
not say so. **The fix is entirely on the data side: raise `BG_N_BENIGN`.** BeaverTails
30k_train has thousands of unused safe rows; the cap is arbitrary.

#### A4. The OOD arm is not OOD.

`load_ood()` reads `BeaverTails/30k_test` — same dataset, same annotators, same taxonomy,
same prompt+response rendering as 93.5 % of train. n=2,787. It measures *split* transfer,
not distribution transfer. README §6 calls it "honest out-of-distribution transfer" and
§10 EXP-E calls it "OOD content"; both overstate it. §10.0 then builds an argument on this
arm ("Training transfers ✔ … EXP-E holds the policies fixed and changes the content"),
and the content barely changes.

`intrinsec-ai/cstm-bench` — the benchmark CLAUDE.md rule 8 names for exactly this lesson
family — **is already downloaded on this host** (`~/.cache/huggingface/datasets/intrinsec-ai___cstm-bench`).
It is free to add.

### B. Correctness / completeness

#### B1. §18.6 claims — BOTH VERIFIED IN CODE

- `ContrastiveBiEncoderGuard` **exists** (`encoders.py:385`), learns `Wc`/`Wp`, multi-positive
  InfoNCE (`encoders.py:462-474`), trained on seen columns only, scores any policy from its
  text. ✔
- Projection init **is** random orthonormal by default (`encoders.py:413` `init: str =
  "orthonormal"`; `encoders.py:456` `torch.linalg.qr(...)`), with `torch.eye` retained
  **only** under `init="truncate"` as a labelled ablation. ✔ The measured justification
  (0.1196 vs 0.0322 mean |cos error|, ~3.7x) is in both the code comment and README §10.0.

**New defect found here: `fit(..., hard_negs=None)` is a dead parameter.** The docstring
one line below says *"InfoNCE over (content, its policies) with in-batch **+ mined hard
negatives**"* and README §10.0 frames the arm against papers that use "InfoNCE-style
contrastive loss **and hard-negative mining**". The body (`encoders.py:419-479`) never
references `hard_negs`. The mined negatives reach only the *separate* `ContrastiveAdapter`
in `hardneg.py` for EXP-F. The `bi_encoder_trained` arm carrying every §10.0/§10.1/§10.2
conclusion is **in-batch negatives only**.

#### B2. EXP-G and EXP-H — VERIFIED PRESENT AND RUN

Both are fully populated in `results.json`, not stubs:
- EXP-G `label_scale_accuracy`: 884 distractors used (1,080 candidates, 0 dropped),
  fingerprint `8c3fc96b2b05`, max Jaccard observed 0.125 vs a 0.20 gate, K grid
  [16,64,256,900], both arms.
- EXP-H `opir_taxonomy`: n_labels **996** = 16 top + 126 mid + 854 leaf, fingerprint
  `8611952dba23`, matched-K 900, both arms, 51-key metric blocks each.
- Artifacts on disk match: `distractor_bank_embeddinggemma.npz` B(884,768),
  `opir_taxonomy_embeddinggemma.npz` B(980,768) [= 126+854 mid+leaf], both carrying a
  `fingerprint` field.

Quality note in their favour: both blocks carry
`per_column_invariance_verified: true` / `cross_experiment_anchor_verified: true` and
explicitly refuse to report the tautologically-flat macro-AP as a scaling result. §10.1's
line — *"Anyone reporting that flatness as 'accuracy is maintained at scale' would be
reporting a tautology"* — is the single best piece of methodology in the lesson.

#### B3. STALENESS — the meerkat defect is half-fixed, and the unfixed half is the older half

`pool_fingerprint`: **absent**. There is no fingerprint over the corpus texts, the labels,
or the policy descriptions. What exists is a fingerprint over the *newer* two banks only:

| cache | validation on reload | stale-safe? |
|---|---|---|
| `distractor_bank_*.npz` (EXP-G) | shape **and** `fingerprint` (`run:513`), logs `cache REJECTED` | **YES** |
| `opir_taxonomy_*.npz` (EXP-H) | shape **and** `fingerprint` (`run:792`) | **YES** |
| **`emb_train_*.npz` / `emb_ood_*.npz`** | **`X.shape[0] == len(texts)` ONLY** (`run:165`) | **NO** |
| **`policy_bank_*.npz`** | **`B.shape[0] == len(policies)` ONLY** (`run:193`) | **NO** |

So the fingerprint discipline was invented for the two experiments added last and **never
retrofitted to the two caches it was invented for**. Concretely:

- Change a policy description or a paraphrase in `_POLICY_SPEC` → still 16 rows → the
  **stale bank is silently reused** and every cosine in EXP-A/B/C/E/G/H is against the old
  text. This is verbatim §18.8's *"the embedding cache returned stale labels under a key
  that ignored them."*
- Change the dataset mix (e.g. wildguardmix starts loading) in a way that lands on the same
  row count → stale content embeddings reused.

**Live evidence this matters, from mtimes alone** (not proof, but the exact shape of the
risk): `emb_train_embeddinggemma.npz` and `policy_bank_embeddinggemma.npz` are both dated
**Jul 27 19:46**, while `encoders.py` was modified **Jul 31 23:18** and `results.json`
written **Jul 31 23:40**. The Jul-31 regeneration that produced every headline number
reused Jul-27 embeddings, and nothing in the code can tell you whether the encoder path
changed in between.

**What is NOT stale (verified):** the corpus itself is fully deterministic — my
from-scratch CPU rebuild reproduced `length_auc` to 16 significant figures and
`n_test_rows` exactly. And the numbers *are* internally consistent. The defect is that
this is luck plus discipline, not enforcement.
