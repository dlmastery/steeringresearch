## 2. Findings

### A. Dataset quality (primary)

**A1. The negative design is BETTER than the brief assumed — and that matters.**
The lesson has two conditions, not one [V, `data.py:load_dataset`, `config.HARD_WINDOW`]:

- **EASY**: positives = Attack_600 `multi_turn_queries`; negatives = UltraChat-200k user
  turns, keyword topic-matched via `C.CATEGORY_KEYWORDS` and turn-count biased.
- **HARD** (`data.py:_build_hard`): both classes drawn from Attack_600 itself. Query_ids
  are shuffled and split in half; positive = the **last 4 turns** of an attack in the pos
  half (contains the payload), negative = the **first 4 turns** of a *different* attack in
  the neg half (benign lead-up, payload excluded). Both classes are exactly 4 turns.

That HARD construction is essentially the same evolution `cross_trajectory` made — a
different attack's benign lead-up as the hard negative — and the README correctly makes
HARD, not EASY, the headline. The keyword-matched UltraChat negative is explicitly framed
as a **cautionary "too-easy" set** and its trivial separability is quantified. Credit where
due: this is the right shape.

**A2. But EASY's negative set is measurably broken, and the README under-reads how badly.**
`totalchar_auc = 0.1133` means benign conversations are *far longer* in characters;
directionless that is **AUC 0.887 from raw character count alone**. And
`turncount_auc = 0.7232` (pos mean 4.995 turns, neg mean 4.315) [V]. So the EASY condition
is separable at ~0.89 by length and ~0.72 by turn count *before any model runs*. Every EASY
number (per_turn_max 0.999, trajectory_mlp 1.000) is at or below the confound ceiling and
carries **zero** information. The README says this ("certifies nothing") but still prints a
4x4 table of EASY AUCs as if they were results; they should be struck or shown as
"<= confound bar". The turn-count biasing in `_load_negatives` demonstrably did not work:
it only skips over-quota turn-counts once the pool is already >= n_neg (`data.py:120-122`),
so at n=200 with a large scan the biasing almost never fires.

**A3. HARD source asymmetry — I checked it, and it is a NON-issue. Reporting the negative.**
In `_build_hard` [V, `data.py:189-194`] positives require `len(turns) >= W` (W=4) while
negatives require `len(turns) > W`, so in principle positives could come from 4-turn attacks
that negatives cannot. I loaded the cached Attack_600 arrow directly: the turn-count
distribution is **{4: 4, 5: 596}** [V]. Only 4 of 600 rows have 4 turns, so the asymmetry
touches at most ~2 positives in a 200-row class. Not a confound. The lesson is clean here.

What the lesson still does **not** report for HARD is the **category balance** per class.
Attack_600 categories are heavily skewed (`illegal` 174, `cybercrime_intrusion` 120,
`misinformation` 102, `chemical_biological` 84, `harmful` 63, `harassment_bullying` 57) [V],
and the pos/neg query_id halves are drawn by an unstratified `rng.shuffle`, so category
proportions can differ between classes by chance. `_build_hard` collects `categories` but
`_run_condition` never reports or stores them for the hard condition [V]. Cheap to add.

**A4. The confound bar is real but incomplete — three missing controls.**
1. `totalchar_auc` sums characters over the whole window. The discriminative object in HARD
   is the **last turn** (payload vs non-payload). A `last_turn_charlen` AUC would very likely
   be higher than 0.752, which would raise the bar the methods must clear.
2. There is **no content bar**: no TF-IDF / bag-of-words AUC, no "logreg on the last turn
   embedding only". The latter is the decisive control. `PerTurnMaxProbe` is a *max* over
   turns, which is not the same as "read only the final turn" — a model that just learns
   "the 4th turn is the ask" would score high and would not be reading a trajectory at all.
   Without that control, "the escalation trajectory is the signal" (README §8) is **not
   established** by these numbers.
3. No **shuffled-turn control**. Permuting turn order within each conversation and re-running
   `seq_gru`/`trajectory_mlp` is the direct test of whether order carries the signal. It is
   ~free (CPU, cached embeddings) and it is the single highest-value missing experiment in
   this lesson. Note `TrajectoryMLP`'s features are mean/last/max/std + mean consecutive
   delta + max drift-from-turn-0 — mostly **order-insensitive**; that the order-insensitive
   model (0.956) beats the order-sensitive GRU (0.725) on Gemma is itself evidence *against*
   the trajectory reading, and the README does not confront it.

**A5. n per class vs the rubric — measured ceilings, not guessed.**
Shipped: 200/200 per condition [V]. Rule 1 floor: 500/class.

I computed the true ceilings from the cached Attack_600 arrow [V]:
- 600 rows, **200 distinct `query_id`s** (3 attack paths per goal, as documented),
  turn-counts {4: 4, 5: 596}.
- **EASY ceiling: 600 positives** (config default already `N_POS=600`) and effectively
  unbounded UltraChat negatives (`train_sft` = 207,865 rows, ungated). So EASY **can meet
  rule 1 today at pure CPU+GPU-embed cost** — 600/600 >= 500/class. The 200/200 shipped is
  an unforced choice, not a limit.
- **HARD ceiling: ~300 positives / ~298 negatives** (rows with >=4 turns = 600, rows with
  >4 turns = 596, halved by the disjoint query_id split) [V]. So HARD **cannot** reach
  500/class from Attack_600 alone — a genuine rule-2 pool limit. But the run used **200 of
  the ~298 available**, i.e. it did **not** maximise within the pool, and the README never
  states the ceiling. That is the rule-2 FAIL, precisely: 200 used vs ~298 available, and
  no sentence saying "the pool caps us at ~300".

**A6. The biggest single dataset finding: the lesson is already loading a dataset whose
larger config it ignores.** `SafeMTData/SafeMTData` has **two** configs [V, HF page + local
arrow]: `Attack_600` (600 rows, used) and **`SafeMTData_1K` (1,680 rows, unused)**. The 1K
config has `conversations` = `[{role, content}]` with user-turn counts
**{1:7, 2:84, 3:175, 4:212, 5:230, 6:969, 7:3}** [V] — i.e. 1,586 conversations with >=4
user turns, and 826 distinct `query_id`s. It is ungated, MIT, and **already fully cached on
this host** (24.7 MB arrow at
`~/.cache/huggingface/datasets/SafeMTData___safe_mt_data/SafeMTData_1K/...`) [V].
Adding it takes HARD from a ~300/class ceiling to **>1,000/class** and clears rule 1.

**CRITICAL implementation warning if you do this:** `query_id` is **not a global key across
the two configs**. Overlap of `query_id` sets: **157 of 200** — but overlap of `plain_query`
sets: **0** [V]. The configs re-index `query_id` independently. Concatenating and grouping
by `query_id` would silently merge 157 unrelated attack goals into shared CV groups, i.e.
manufacture fake groups and corrupt the leakage discipline the lesson is proud of. **Group
by `plain_query`** (or by `(config, query_id)`), which gives 200 + 826 = 1,026 clean groups.
This is exactly the §18.8 silent-and-plausible failure mode; it would not crash.

### B. Correctness / completeness

**B1. EmbeddingGemma compliance: NON-COMPLIANT. FAIL.** [V]
- `config.EMBEDDERS` defaults to `"both"` = `["gemma", "minilm"]` (`run_multiturn._embedder_list`).
- `embed.get_embedder` supports exactly two methods and **raises** on anything else:
  `"method must be 'gemma' or 'minilm'"` — there is no EmbeddingGemma code path at all.
- The `"gemma"` arm is **not** EmbeddingGemma. It is `models/google/gemma-3-1b-it`, a
  decoder LM, mean-pooled layer-12 residual activation (`embed._get_gemma_embedder` ->
  `hello_world_steering.model_utils.mean_pool_activation`), dim 1152 [V, npz `dim=1152`].
- `"minilm"` is `sentence-transformers/all-MiniLM-L6-v2`, dim 384 [V] — the encoder the
  user's standing guidance explicitly forbids.
- MiniLM is **not** a discarded arm. README §8 headlines it: "MiniLM's `seq_gru`/`hier_attn`
  reach 0.83-0.85" and the falsifier-cleared sentence quotes "MiniLM 0.849 vs 0.569" as one
  of the two supporting legs. `artifacts/auc_by_method_embedder.png` is the method x embedder
  comparison. So MiniLM numbers are headline numbers.
- **The blocker CLAUDE.md §18.5 records ("`google/embeddinggemma-300m` is gated; this host
  has no HF token") no longer holds.** I verified file *contents*, not a listing:
  `~/.cache/huggingface/hub/models--google--embeddinggemma-300m/snapshots/57c266a.../model.safetensors`
  is **1,211,486,072 bytes**, plus `2_Dense/model.safetensors` and `3_Dense/model.safetensors`
  (9.4 MB each), `tokenizer.json` 33 MB. The weights are on disk. The swap is unblocked.

**B2. Artifact staleness — the meerkat defect is present. FAIL.**
`results.json` cannot be regenerated from the code beside it today.
- `config.N_POS`/`N_NEG` default to **600/600** [V], but the shipped run is **200/200** [V].
  The only way to get 200 is `MJ_N_POS=200 MJ_N_NEG=200` at runtime. Those values are
  **recorded nowhere** — not in `results.json`, not in README §7 (whose env table lists the
  defaults as 600), not in a run command. Running the documented command today produces a
  different dataset and different numbers.
- There is **no pool/config fingerprint guard** of the kind `meerkat` had to add. `results.json`
  stores `gemma_model_id, gemma_layer, minilm_id, min_turns, max_turns, seed, n_folds, judge`
  — but not `n_pos_requested`, `n_neg_requested`, `HARD_WINDOW`, `EMBEDDERS`, a data hash, a
  commit SHA, or a timestamp [V].
- `MJ_HARD_WINDOW` is not in README §7's env table at all [V]; changing it silently changes
  the HARD dataset with no record in the artifact.
- The embedding caches that would let a reader re-derive the numbers without a GPU are
  `.gitignore`d (see rule-9-extra above), so the artifact is unreproducible *and*
  unverifiable from the repo.
- `embed.load_or_build` validates the cache only by `len(cached) == len(conversations)` [V].
  A cache built at n=200 with a *different seed or different HARD_WINDOW* would be silently
  reused as long as the count matches. This is precisely the §18.8 "stamp your inputs"
  failure mode: silent, plausible, wrong.

**B3. Dead config + a README path that does not exist.**
`config.EMB_CACHE`, `config.ROC_PNG` (`roc_by_method.png`), `config.BAR_PNG`
(`auc_by_method_embedder.png`), `config.TRAJ_PNG` (`risk_trajectory_example.png`) are all
unused — `run_multiturn._run_condition` builds its own per-condition paths
(`roc_%s.png`, `auc_%s.png`, `risk_trajectory_%s.png`) [V]. README §3 tells the reader the
trajectory plot is `artifacts/risk_trajectory_example.png`; that file **does not exist**
(the directory has `risk_trajectory_easy.png` / `_hard.png`) [V]. `auc_by_method_embedder.png`
does exist but is a leftover from an earlier single-condition run (mtime 06:24, before the
easy/hard artifacts at 06:57/07:04) and is **not** written by the current code — a stale
binary shipped in the repo.

**B4. README §5's walkthrough of `run_multiturn.py` is stale.** It describes a
single-condition `main()` ("`data.load_dataset()`; print counts and the confound report;
then for each embedder..."). The actual `main()` loops over `_condition_list()` and delegates
to `_run_condition` [V]. Section 8 does describe both conditions, so this is an internal
inconsistency inside the README, not a hidden one.

**B5. Group-aware CV: correct in EASY, degenerate-ish in HARD.**
EASY: attack groups are `query_id`, benign groups are `10_000_000+i` (one per conversation)
[V] — correct. HARD: groups are query_ids, and pos/neg query_id sets are **disjoint by
construction** [V, `_build_hard`]. `GroupKFold` will therefore never place a positive and
its own negative counterpart in the same fold — fine — but it also means fold class balance
is uncontrolled (no stratification), and with ~100 pos qids + ~100 neg qids at 5 folds a
fold could skew. `_metrics` pools out-of-fold scores across folds before computing AUC, so
per-fold miscalibration between folds contaminates the pooled AUC. Pooling raw
`predict_proba` across independently-fit models is a real (if common) methodological wart;
per-fold AUC + mean/CI would be cleaner.

**B6. `hier_attn` Gemma AUC = 0.446, TPR@FPR10 = 0.000.** Reported honestly in README §8
with a warning glyph [V]. Below chance with a CI of [0.394, 0.499] that **excludes 0.5** —
i.e. it is significantly *anti*-correlated, which is a stronger statement than "failed to
train" and usually indicates a label/fold artifact rather than mere overfitting. The README's
explanation ("overfits high-dim inputs at n~200") does not account for a systematic
below-chance result. Worth a look, not just a caveat.

**B7. `bootstrap_auc_ci` uses a fixed `seed=0` default and is never varied.** Single seed
throughout (`C.SEED=0`, `_set_seeds` in `models.py`) [V]. Consistent with the screening-tier
label; noted so nobody mistakes the bootstrap CI for a seed-variance CI. The bootstrap CI
measures sampling noise on one fixed fit, not training-run variance.

### Tier 1 — do these first (they change what the lesson is allowed to claim)

1. **[MEDIUM] Add the shuffled-turn control.** `run_multiturn.py`: add a `MJ_SHUFFLE_TURNS`
   arm that permutes each conversation's turn order (fixed seed) before CV and re-scores
   `seq_gru` / `trajectory_mlp` / `hier_attn`. Runs entirely on the **cached** `.npz`
   embeddings — no GPU, minutes. This is the decisive test of the lesson's one thesis. As it
   stands, the order-**insensitive** `trajectory_mlp` (Gemma HARD 0.956) beats the
   order-sensitive `seq_gru` (0.725), which is evidence against "the trajectory is the
   signal" that README §8 does not confront. Highest value per unit cost in the whole lesson.

2. **[MEDIUM] Add a `last_turn_only` control model.** `models.py`: a logreg on the **final
   turn embedding alone**, exposed as a 5th entry in `config.METHODS`. `PerTurnMaxProbe` is a
   *max over turns* and is NOT this control. If `last_turn_only` scores near 0.95 on HARD,
   then the HARD result is "the payload turn is recognisable", not "escalation is
   detectable", and the headline must be rewritten. Cached embeddings, CPU.

3. **[CHEAP] Record the run config in `results.json` and assert the anchor.**
   `run_multiturn.main()`: add `n_pos_requested`, `n_neg_requested`, `hard_window`,
   `embedders`, a `sha256` of the loaded conversation list, the git commit, and a timestamp.
   Then in `embed.load_or_build`, replace the `len(cached) == len(conversations)` check with
   a stored-fingerprint equality check that **raises** on mismatch (`embed.py:114-119`).
   Today a cache built at a different seed/HARD_WINDOW is silently reused if the count
   matches — the meerkat defect, live in the code.

4. **[CHEAP] Stop `.gitignore`-ing the embedding caches.** Delete `*.npz` from
   `steering_tutorials/multiturn_jailbreak/artifacts/.gitignore` and force-add the four
   `seqs_*.npz` (21 MB total). CLAUDE.md §17 requires binary artifacts be force-added "so
   each lesson reproduces from the repo". Right now every number in the README is
   unverifiable by a cloner without a GPU.

## Overall

The **scientific design is better than most lessons in this course**. The EASY/HARD
two-condition contrast is the right idea, the hard negatives are genuinely leakage-free and
length-matched, a confound baseline **is** computed and quoted (this is *not* the trajguard
defect), the failed `hier_attn` cell is reported rather than hidden, and all three arXiv
citations verify exactly with no misattribution.

What fails is **execution against the rubric**: n is 200/class against a 500 floor, with ~298
available in-pool and 2,280 more sitting ungated and pre-cached in the same HF repo; there is
no OOD arm; the embedding caches are gitignored; the artifact records none of the config that
produced it; MiniLM is still a headline embedder; and the two controls that would actually
establish "trajectory" over "the last turn is the ask" — shuffled-turn and last-turn-only —
are missing, while the lesson's own numbers hint they might not survive them.
